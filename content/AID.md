_AID - Artificial Intelligence Driven Development_
## Ключевые идеи
- Теперь ты не программист, а архитектор! Фокус на более масштабных вещах и бизнесе, а не на коде от твоих рук.
- Когнитивная нагрузка должна быть минимальной! Минимальной с учетом масштаба системы. Еще более строгими становятся требования по Coupling, Cohesion, выделению и контролю утечек абстракций, чистоте функций, их размеру, размеру файлов и так далее.
- Чем более распространенная технология или подход – тем лучше.
- Чем более надежный подход тем лучше.
- Как можно больше качественной документации в кодовой базе. Различные README и Docstring лучшие друзья GDD.
- Рекомендуется использовать DDD, layered architecture.
- Тесты обязательны.
- Линтеры обязательны.

## Наблюдения
* Архитекторский подход реально работает для восприятия
* Рефакторинг с моделью таки не очень т.к. ллм теряет детали
* Лучше снова писать с нуля, чем пытаться переделать с моделью
* Модели на стали на столько сильными, чтобы справляться с большим числом абстракций за раз
* Вайбеодинг это большой труд, т.к. он требует еще более высокого уровня программирования и архитектуры, чтобы не ломаться. Нужно продумывать ментальную сложность системы, иначе модель начнет ошибаться, нужно продумывать инструменты, тоже влияет на ошибки. Нужно больше тратить сил на контроль качества (тесты), иначе можно пропустить ломающее изменение. Зато в замен получаем скорость в 3 раза выше при большем качестве (можно проводить аналогию между велосипедом и мотоциклом). Но возможно если улучшить практики самого процесса, то труда будет меньше.
* Пока кажется что кодовая база и правда лучше на выходе. GDD (Generation) в этом похож на TDD т.к. создает требования к проекту быть более понятным и структурированным
	* В итоге ГДД тянет за собой и хорошие практики кода и архитектуры и тестов
	* От части это от того, что для надежности нужны тесты, а тесты тоже тянут архитектуру в нужном направлении
* Не всегда ясно чего хочешь и в таких моментах просто сам пишешь

## GDD и модульность
* **Нужна максимальная изоляция** - чтобы понизить стоимость на переписывание
* **Стоит очень нежно относится к контрактам** - чтобы не завязаться на вайбкод и не потерять все плюсы низкой цены на реинжениринг
* **Тесты-тесты-тесты** - чтобы реально фиксировать состояние и реально можно было много переписывать каждый раз
* Можно идти в MCP-style микросервисы, но пока есть возможность, лучше все равно оставить модульный монолит
## Cognitive-enrichment

Before process add these files:
* `.cursorules`
* `AGENT.md`

Rules:
* File less then 400 lines
* Do from deepest to shallowest (from ./.../.../....../module/file to ./)
* For services and apps `README.md`, for modules `DESCRIPTION.md`

For docstrings:
```md
Add docstrings for this code for explanations, use Google Python Style Guide for it
```

For readme and descriptions:
```
@CURRENT_TASK.md. Give me readme for module
```

```md
I have module and need documentation for it. It must contain description and some abstract logic that is out of docstring context.
Also skip deploy and test part, it will be in another file.

Additional info:
* Use AGENT.md in root dir for rules and info
* Use READ.md files to understand project

Context:
This is module for helpdesk integration
```

* Опционально можно сначала добавить агентные файлы (например для курсора)
* Все рекурсивно (от комментов к полному README.md)
* Документы должны соответствовать уровню, информация не должна протекать снизу вверх абстракции
	* Например: в документе проекта не должно быть информации об интерфейсе функции какого-то модуля
* При этом обратное допустимо. Информация об общем может быть в частном.
	* Например: в абстрактном классе краткое описание общей архитектуры, чтобы было понятно как он работает в композиции с остальным кодом
* Алгоритм (все в основном при помощи LLM, но нужно проверять и править):
	1. Идем по каждому модулю, от самого глубокого к корневому
		* При этом каждый раз думаем какой контекст понадобится, чтобы написать хорошую доку: для утилиты хватит и ее самой, для main понадобится контекст всего приложения.
	2. Прописываем docstring (с указанием что потом будем использовать sphinx) в каждой сущности кода
	3. Добавляем комментарии внутри функций по надобности
	4. Когда описали все файлы в модуле (подмодули для питона), создаем общий файл с более абстрактным описанием всего модуля.
	5. В корневом модуле описываем архитектуру и структуру всей системы
	6. В корне проекта создаем README с описанием проекта, ключевыми идеями, описанием деплоя, тестирования и инструментов для работы с проектом.

## Секретные техники глубинных вайбкодеров

Длинная задача (фича с более чем тремя абстрактными пунктами ТЗ):
* Прописываем задачу и доп. контекст
* Доводим план до 

Жадный алгоритм:
* Пытаемся выполнить задачу любой ценой (любое качество кода, возможно даже любой подход)
* Фиксируем тестами
* Рефакторим и реинженирим

> Общая идея в том, что мы жадно доходим до оптимума решения, а далее зная локацию искомой точки оптимизируем маршрут
